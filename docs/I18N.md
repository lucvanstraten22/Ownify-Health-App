# Language and units

Ownify speaks Dutch and English, and shows measurements in metric or
imperial units, on the website and in the Android app alike. This is how,
and the rules a new screen, string or number has to follow.

In code: `includes/i18n.php` (the server), `assets/js/i18n.js` (the
website's scripts), `OwnifyAndroid/app/src/main/java/com/ownify/android/i18n/OwnifyI18n.kt`
(the app). The three follow the same rules and are tested to write the same
things (`tools/i18n-test.php`, the app's `I18nTest`).

---

## The language

### Which one

Per request, the first that applies wins:

| | where | when |
|---|---|---|
| 1 | `user_profiles.locale` (`nl`, `en`) | the signed-in account chose one in Instellingen › Taal |
| 2 | cookie `ownify_lang` (website) or `shared_prefs/ownify_language` (app) | this browser or phone chose one: the screens before signing in and after signing out |
| 3 | the device | the browser's `Accept-Language`, or the app's: its own choice when made, else the phone's language |
| 4 | Dutch | |

The device's language is its **first** language: English (`en`, `en-GB`,
`en-US`…) is English, Dutch is Dutch, **anything else is Dutch** — a German
phone is not an English one, even with English second.

**Automatisch** (the first option under Taal) means "follow the device": it
is NULL in the database and no cookie, never a stored `nl` or `en`. Only an
explicit Nederlands or English is ever kept. Before migration 021 every
account had `locale = 'nl'` as a column default nobody chose; the migration
makes those NULL.

### Kept, and the same everywhere

A choice is saved on the account (`api/profile/preferences.php`), so it is
the same on the website and in the app, and survives reloading, restarting,
signing out and signing in. The website also writes the cookie, and the app
its preference, so the screens without an account (the opening screen,
signing in, registering) stay in the chosen language after signing out. A
choice applies at once: the website reloads the page, the app reads its
state again (`i18n` in `api/app/state.php`) and every screen follows
(`OwnifyLanguage` is Compose state).

The app sends its language as `Accept-Language` on every request; the
server answers in it and says in the state what is in force:

```json
"i18n": { "locale": "en", "chosen": null, "units": "imperial" }
```

`chosen: null` is Automatisch.

### The catalogue

Ownify is written in Dutch: every string in the code and the config is the
Dutch one. **`lang/en.php` is the one English catalogue**, keyed by that
Dutch, kept in parts by area in `lang/en/*.php` — one Dutch sentence has
one English, wherever it appears.

| where | how |
|---|---|
| PHP | `t('Opslaan')`, `tf('Nog %d dagen', $n)` (sprintf), `tn($n, '%d dag', '%d dagen')` |
| config | `config_copy('goals')` instead of `require`: every Dutch leaf translated, identifiers (`id`, `key`, `icon`, `unit`… — `I18N_IDENTIFIERS`) left alone |
| API answers | `api_json()` translates `error` and `message`, so `api_fail('Vul een waarde in.')` arrives in English |
| scripts | `var T = window.OwnifyI18n;` then `T.t('…')`, `T.tf('…', …)`, `T.tn(n, '…', '…')` |
| Kotlin | `tr("…")`, `trf("…", …)`, `trn(n, "…", "…")` |

A string without English stays Dutch — never empty, never a key.

The scripts and the app only need the strings they write themselves, so
they get a generated subset: `assets/js/lang-en.js` (loaded only on an
English page) and `OwnifyAndroid/app/src/main/assets/lang-en.json`.

```
php tools/i18n-build.php           write both subsets
php tools/i18n-build.php --check   change nothing; fail when a subset is out of
                                   date, a string asked for has no English,
                                   placeholders differ, or a call's argument
                                   is not a literal
```

The argument of every `t`/`tr` call must be the **literal Dutch**, in one
piece: `T.tf(x ? 'maximaal %s' : 'minstens %s', v)` or
`tr("a " + "b")` cannot be found, so its English would never reach the
subset. Write `x ? T.tf('maximaal %s', v) : T.tf('minstens %s', v)`.

**Adding a string:** write the Dutch in a `t`/`tr` call, add the English to
the right part of `lang/en/`, run `php tools/i18n-build.php`, commit all
three.

### Stored text stays Dutch

What Ownify itself writes into the database stays Dutch and is translated
when it is shown, so it follows the reader's language today rather than
the one in force when it was written:

- point rules and the points ledger (`point_rules.label`, ledger notes)
- a cloud source's last error (`user_integrations.last_error`,
  `integration_message_shown()`)
- the one-time messages after a redirect (`auth_flash_take()`)
- an AI proposal's confirmation and refusal

What people write — names, goals, notes, messages, AI conversations — is
never translated.

### Numbers, dates, plurals

| | Dutch | English |
|---|---|---|
| numbers | `1.234,5` | `1,234.5` |
| `day_month` / `day_mon` | 5 oktober / 5 okt | October 5 / Oct 5 |
| `weekday_day_month` | maandag 5 oktober | Monday, October 5 |
| `day_mon_year` | 5 okt 2026 | Oct 5, 2026 |
| `numeric` | 5-10-2026 | 10/5/2026 |
| plurals | `tn(1, '%d dag', '%d dagen')` → 1 dag | 1 day |

`i18n_number()`, `i18n_date()` and their twins `T.number()`/`T.date()` and
`OwnifyFormat.number()`/`.date()`. Rounding is half away from zero on the
shortest decimal everywhere (2.355 → 2.36), as PHP's `number_format`.

A typed number is read either way: "72,5", "72.5", "1.234,5" and
"1,234.5" are all what they look like (`i18n_parse_number()`,
`T.parseNumber()`, `OwnifyFormat.parseNumber()`).

## The units

Instellingen › Voorkeuren › Eenheden: **Metrisch** (the default) or
**Imperiaal**, kept as `user_profiles.units` (NULL is metric), on the
account like the language.

| | stored (always) | metric | imperial |
|---|---|---|---|
| distance | km (or m) | km | mi |
| elevation | m | m | ft |
| weight | kg | kg | lb |
| height | cm | cm | ft/in ("5 ft 11 in") |
| temperature | °C | °C | °F |
| speed | km/h | km/h | mph |
| pace | seconds per km | min/km | min/mi |

**Nothing stored ever changes.** Every measurement is kept as it always
was. The units decide only how a value is **shown** — converted at the
presentation boundary (`units_out()`, `units_format()`, `units_label()`,
`units_pace()`) — and how a typed value is **read** — converted back at the
input boundary (`units_in()`, `units_canonical()`,
`units_parse_feet_inches()`). So nothing is converted twice, nothing is
stored rounded, and switching back and forth changes no row.

A form says which units its figures were typed in: the profile's `*_unit`
fields, and a goal's own unit. A request that does not say — an app from
before 15.0 — typed metric, as it always did.

A goal has its own unit (`goals.unit_code`, chosen in the wizard, starting
as the reader's: lb for an imperial reader's weight goal): a weight goal of
176 lb is stored as 79.8 kg, once, and shown as 176 lb again — on its page, in
its chart, in what is logged on it — whatever Eenheden says later
(`goal_unit()`, `goal_to_stored()`, `goal_value_text()`; docs/GOALS.md). A
goal's typed figures are read the reader's way, and "10.000" in Dutch is ten
thousand (`goal_parse_number()`).

A height typed in imperial may be written `5'11`, `5 ft 11 in`, `5 11`, or
inches (`71`); a lone whole number from 2 to 8 is feet (`6` is 6 ft —
nobody is six inches tall), `6 in` is inches.

Charts draw what they are given, in the reader's units, on the same time
axis as always (docs/CHARTS.md); only the numbers and the unit change.

Not converted: water (litres), energy (kcal), nutrients (grams), heart rate,
steps, sleep and durations — they are the same in both systems.

## The first day of the week

Instellingen › Voorkeuren › Eerste dag van de week: **Maandag** (the default,
as in the Netherlands) or **Zondag**, kept as `user_profiles.week_start`
(NULL is Monday, migration 024) on the account, like the units, and saved at
once (`api/profile/preferences.php`, `week=sunday|monday`). It decides where
a week begins wherever Ownify lays days out in weeks:

- a goal's day calendar (Per dag): its weekday initials (`week_initials()`,
  on Android `OwnifyPreferences.weekInitials()`) and the empty days before
  the first one (`goal_calendar()`, `week_first_day()`);
- OwnifyAI's weekly totals (`per_week`, keyed by each week's first day; the
  context says which day that is).

Charts over time are not weeks: they keep the period's own window and dates
(docs/CHARTS.md), whatever the week's first day is.

## The AI assistant

The assistant answers in the reader's language and units:
`config/ai-prompt.php` gets `{language}` and `{units}`
(`includes/ai/prompt.php`), and the context names both
(`includes/ai/context.php`). The data it reads stays as stored — metric —
and the prompt tells it to convert when it speaks in imperial. What it may
read, its formulas, its consent and what it may do are unchanged. If a
person writes to it in another language, it answers in that language.

Conversations are stored as they were written, in the language of the
moment; they are not translated afterwards.

## The Android app

- `OwnifyLanguage` — the language (`locale`), the choice (`chosen`, null
  for Automatisch) and the units, as Compose state; restored before the
  first frame (`MainActivity`, `PermissionsRationaleActivity`), adopted from
  every state read, kept in `shared_prefs/ownify_language`.
- `tr`, `trf`, `trn` — the catalogue from `assets/lang-en.json`.
- `OwnifyFormat` — numbers, dates and the parser, as the server's.
- `OwnifyUnits` — the units, as the server's; most values arrive from the
  server already converted, so the app converts only what it writes itself.

The unit tests run on a Dutch phone, whatever the machine is
(`build.gradle.kts`: `user.language`; `src/test/resources/robolectric.properties`:
`qualifiers=nl-rNL`, a class adding its own with a leading `+`). A test of
English asks for it outright (`OwnifyLanguage.use("en", …)`).

## Tests

- `php tools/i18n-test.php` — device detection, the choice kept across
  reload, logout and login, the catalogue check, numbers, dates, every
  conversion both ways, goal units, and, over HTTP: the signed-in website,
  the app's state, the opening screen, the setup and the first days in
  English with no Dutch left, imperial on every page without a stored row
  changing, imperial input stored metric, and back.
- `php tools/i18n-build.php --check` — part of the above.
- The app's `I18nTest` and `PresentationHelpersTest` (Gradle
  `testDebugUnitTest`).

## Not (yet) translated

- A publication's title (docs/RESEARCH.md): it stays exactly as published, in
  its own language — marked as such for screen readers (`lang` on the
  website, a `LocaleList` span in the app) and said under it when it is not
  the reader's ("The publication is in Dutch."). `tools/i18n-test.php` leaves
  text marked `lang="nl"`, and a title beside `"language": "nl"` in the app's
  state, out of its Dutch search; everything around it — the findings, the
  citation, the labels — is translated.
- Text that was stored in English or Dutch by people, and AI conversations.
- Third-party pages: Google's and Polar's sign-in screens, Health Connect.
- Health Connect's own permission screen lists its data types in the
  phone's language, not Ownify's.
